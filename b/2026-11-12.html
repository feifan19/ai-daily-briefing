    上下文压缩已是常规操作，但现有检查只比答案或最可能词，会漏掉一种常见失败：关键证据被删、答案却不变，答案失去支撑、别的模型复用这份上下文时就有风险；SELD 无需训练与标签即可检测；上上下文压缩前先跑证据保留检查，别只看答案对不对。
    来源：arXiv
  • 删除推理历史的代价因模型而异：多轮工具会话的三条件实测
    推理模型每轮工具调用都写推理轨迹、后轮读历史；9.4 万条 ShareGPT 对话里 73% 的用户交互跨越多轮；跨厂商转发会删历史，论文首次直接盲测多轮工具调用中完整删除推理历史的任务代价；跨厂商转发 Agent 会话前先测删历史对任务成功率的影响，别默认历史可有可无。
    来源：arXiv
  • 稠密奖励值得它花的 token 吗？GRPO 的成本账
    GRPO 给解法每个 token 相同 credit，稠密过程奖励用蒙特卡洛采样后续步骤逐步骤打分；只按单次更新比成本会漏掉采样开销，在该设定里采样后续步骤占了绝大部分开销；上稠密奖励前先把采样成本算进训练预算，别只看收敛步数。
    来源：arXiv
  • One Byte, One Token：把 27B 模型直接转成纯字节级
    字节级 BPE 切中文很碎，Qwen3.8 在中文维基上平均 3.84 字节/token、64% 是单字 token，还把拼写信息藏起来；论文把已训好的 27B 子词模型直接转成纯字节级模型（每字节一 token），词表从 248,320 缩到 384；中文 token 成本高的团队先对照字节级方案的拼写与成本收益，别只调分词参数。
    来源：arXiv
  • OpticalRAG：用像素空间压缩给 RAG 省 token
    RAG 的瓶颈在 token 预算，喂长文档贵、激进压缩又会丢细节；论文把渲染后的文本页用视觉编码器压成约一百个视觉 token，语义损失小；长文档 RAG 先对照“像素级压缩”与文本压缩的召回与成本，别只加上下文长度。
    来源：arXiv
  • ARE-bench：测研究 Agent 在真实进行中的项目里能不能交付
    研究 Agent 基准分越来越高，但不等于在真实项目里可靠；ARE-bench 测 Agent 在有未完成文件、过时版本、失败尝试的工作区里接着做一步的能力；选研究 Agent 前先在自家真实工作区复测，别只看基准分。
    来源：arXiv
  • Coding Agent Memory Post-Training II：用 on-policy 蒸馏解锁长程记忆
    长程任务历史常超上下文，Agent 得决定写什么、读什么、何时做；近期工作用 on-policy 蒸馏把记忆控制做进策略，但记忆工具与压缩协议在预训练之外，teacher 给不了有效指导；给长程 Agent 加记忆前先确认记忆接口是否在训练分布内，别只看记忆容量。
    来源：arXiv
  • REAL Loss：直接优化投机解码的真实期望接受长度
    投机解码的加速取决于期望接受长度（EAL），交叉熵、KL 只管分布匹配，块级目标也只是 EAL 的替代；REAL Loss 直接优化真实 EAL；调投机解码先按 EAL 拆收益，别只看分布指标。
    来源：arXiv
  • Multi-Future Drafting：续写会分叉时，别让草稿树拼“嵌合体”
    块草稿器一次前向起草一块未来 token，草稿树按概率乘积验前缀；续写可能分叉时，乘积会把不同未来的前缀拼成目标模型从不产生的“嵌合体”，还分走预算；混合块草稿器解决这个问题；上树验证投机解码前先核对分叉续写下的接受长度，别只看单路径加速。
    来源：arXiv
  • ReTrace：把工具型 Agent 蒸馏成无规划器工作流
    同一个 SOP 在新输入上反复跑，LLM Agent 每步都调 LLM 选下一步，延迟与成本随规模涨；ReTrace 把 SOP 与少量已记录的 Agent 运行转成可复用工作流，由代码而非 LLM 选下一步；高频重复 SOP 先沉淀成代码工作流，别每步都调模型。
    来源：arXiv
  • SteerDistill：用闭环 teacher steering 量化 LLM Agent
    低比特量化降 Agent 推理成本，但会丢任务成功率；失败 rollout 里量化 Agent 会忽略任务要求或环境条件；SteerDistill 用闭环 teacher steering 做量化感知蒸馏；量化 Agent 前先在失败用例上对照量化与全精度行为差异，别只看平均分。
    来源：arXiv
  • 苹果：更快的检索带来更好、更高效的 RAG
    苹果 ML 研究博客文章，用学到的支撑函数做最大内积搜索的路由与查询改写，加速 RAG 检索；做 RAG 延迟优化的团队先读这篇的方法部分，对照自家召回链路看能否复用，别只把链接加入待读清单。(Hacker News，单信源）
